# 实现中的工程原理

## 为什么对话和文稿版本分开保存

AI 说“已经修改”是一个消息，磁盘上的文件是否变化是另一个事实。系统保存两者之间的联系，却不把消息当作文件。一次纯讨论仍有轮次记录；只有真实内容变化才有 V2、V3。缺旧稿就标为缺失，避免把不完整历史包装成可靠证据。

每个版本保存完整内容和 SHA-256 哈希。哈希可以理解为内容指纹：判断两个内容是否一样很方便，但“以前出现过”不代表“本轮没变化”。例如 V1=A、V2=B，再恢复 A，应该得到 V3=A，保留这次恢复行为。

## 为什么“第二段”不能当永久编号

第二段是当时的位置。前面插入一段后，它就成了第三段。记录因此同时保存版本、段落编号和原文；历史批示仍指向原版本。唯一且完全一致的段落可以确定对应关系；明确指定的单段修改也可以关联。拆分、合并或不明确的改写留待确认。错误关联会污染后续经验，比暂时缺一个关联更难发现。

## 断网和进程退出时如何保住记录

本地 JSON 先写临时文件、刷新到磁盘，再通过系统的原子替换动作换成正式文件。读者看到的是旧文件或完整新文件，不会看到写到一半的 JSON。进程锁避免两个采集器同时读旧状态，然后互相覆盖新增轮次。

本地保存与远程网络请求无法合并成一次原子操作，所以要用待同步队列。稳定事件编号让重复执行可以辨认同一轮；远端是否收到需要另行核验。网络超时最棘手：可能对方已保存、但回执没回来。程序应先查远端，保留“不确定”状态，而不能直接宣布失败或成功。

## 为什么为文稿建立独立 Git 仓库

Git 的暂存区是多人和工具共用的。简单执行 `git add .` 再提交，可能把用户正在准备的其他改动也带进去。连接程序只提交已知资产路径，并使用独立资产仓库，将代码开发与写作记录的提交分开。

JSON 记录是可迁移的事实资产，Git 提供差异、历史及同步；Langfuse 用于查看运行过程和反馈。它们承担不同用途，因此 Langfuse 暂时不可用时，原文和版本仍完整保存。

## 为什么候选、发布、加载是三个动作

模型提出“以后都先写结论”，只是一个假设。它可能把一次性要求误推广。候选必须包含用途、读者、来源轮次和适用范围，经人审核后才能发布；发布依据是 GitHub 的真实合并和审核记录。

已经发布也不意味着某次写作用了它。系统先导出适用经验，在使用者确认已将文件交给 AI 后，才登记加载版本。否则后续即使文稿质量变好，也无法判断是否和这条经验有关。

撤销不删除旧证据：新任务排除撤销经验，历史任务仍说明当时用了什么。这样发现错误经验后，既能停止继续传播，也能回溯受影响的写作。

## 测试到底证明什么

自动化测试检查可重复的程序行为，例如相同事件不会重复建版本、插段不会移动旧批示、缺失记录不被补造、网络失败保留队列。用假 HTTP 服务和临时 Git 仓库可以稳定制造这些边界。

这些测试不能代替 Codex 桌面真实关闭、团队 GitHub 审核、真实 Langfuse 核验和同事试用。因此验收记录将本地自动测试与外部实测分开标记，避免把“测试通过”说成“团队已经用起来”。
